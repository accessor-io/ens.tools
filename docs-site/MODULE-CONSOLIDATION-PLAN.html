Module Consolidation Plan

Generated: 2025-01-27 Status: Analysis Complete, Recommendations Ready

🎯 Consolidation Opportunities

1. Seaport Services ⚠️ HIGH PRIORITY

Current State: 4 separate files
  • seaport-service.ts - Core Seaport operations
  • seaport-advanced.ts - Advanced features (collection offers, bundles)
  • seaport-signer.ts - Order signing utilities
  • seaport-error-handler.ts - Error handling
    • Problem:
  • Fragmented functionality
  • seaport-advanced.ts wraps seaport-service.ts
  • Error handling is separate utility
  • Signing is separate utility
    • Recommendation: Consolidate into single seaport-service.ts New Structure: 
    // src/lib/services/seaport-service.ts
export class SeaportService {
  // Core operations (from seaport-service.ts)
  // Advanced features (from seaport-advanced.ts)
  // Signing utilities (from seaport-signer.ts)
  // Error handling (from seaport-error-handler.ts)
}

// Keep separate exports for utilities if needed
export { SeaportErrorHandler, SeaportErrorType } from './seaport-service';
    Benefits:
  • Single source of truth for Seaport operations
  • Easier to maintain
  • Better code organization
  • Reduced import complexity
    • Files to Merge:
  • seaport-advanced.ts → merge into seaport-service.ts
  • seaport-signer.ts → merge into seaport-service.ts (or keep as utility exports)
  • seaport-error-handler.ts → merge into seaport-service.ts (or keep as utility class)

    • 2. Marketplace Services ⚠️ MEDIUM PRIORITY

    Current State: 2 separate services
  • ens-marketplace-service.ts - ENS-specific marketplace operations
  • opensea-marketplace-service.ts - General OpenSea integration
    • Analysis:
  • Both use SeaportService
  • ens-marketplace-service.ts focuses on ENS domains
  • opensea-marketplace-service.ts is more general (NFTs + ENS)
  • Some overlap in functionality
    • Recommendation: Keep separate but clarify boundaries Option A: Keep separate (Recommended)
  • ens-marketplace-service.ts - ENS domain-specific operations
  • opensea-marketplace-service.ts - General NFT marketplace operations
  • Clear separation of concerns
    • Option B: Consolidate with domain-specific methods 
    // src/lib/services/marketplace-service.ts
export class MarketplaceService {
  // General marketplace operations
  // ENS-specific methods (prefix with ens)
  // NFT-specific methods
}
    Recommendation: Keep separate - They serve different purposes:
  • ENS marketplace is domain-focused
  • OpenSea marketplace is general NFT marketplace
  • Different use cases and APIs

    • 3. Transaction Tracking ⚠️ MEDIUM PRIORITY

    Current State: 2 separate services
  • transaction-manager.ts (services/) - Transaction queue, status tracking, retry
  • transaction-tracker.ts (security/) - Transaction tracking with audit logging
    • Analysis:
  • transaction-manager.ts - Queue management, status polling, retry logic
  • transaction-tracker.ts - Audit logging, transaction interception
    • Recommendation: Consolidate into transaction-manager.ts New Structure: 
    // src/lib/services/transaction-manager.ts
export class TransactionManager {
  // Queue management (from transaction-manager.ts)
  // Status tracking (from transaction-manager.ts)
  // Audit logging integration (from transaction-tracker.ts)
  // Transaction interception (from transaction-tracker.ts)
}
    Benefits:
  • Single transaction management system
  • Unified transaction lifecycle
  • Better integration between queue and audit logging
    • Migration:
  • Move transaction-tracker.ts functionality into transaction-manager.ts
  • Update imports across codebase
  • Keep audit logging as optional feature

    • 4. Event Tracking ⚠️ LOW PRIORITY

    Current State: 2 separate services
  • event-tracker.ts - General application event tracking
  • delegate-event-tracker.ts - Delegate-specific blockchain event tracking
    • Analysis:
  • event-tracker.ts - UI events, user actions, application events
  • delegate-event-tracker.ts - Blockchain event queries (DelegateAdded, DelegateRemoved)
    • Recommendation: Keep separate - Different purposes:
  • event-tracker.ts - Application-level event tracking
  • delegate-event-tracker.ts - Blockchain event querying (specialized)
    • Alternative: Rename for clarity
  • event-tracker.ts → app-event-tracker.ts or analytics-tracker.ts
  • delegate-event-tracker.ts → Keep as is (or blockchain-event-tracker.ts)

    • 5. Registry Services ⚠️ LOW PRIORITY

    Current State:
  • registry-service.ts - General registry service
  • Multiple registry components (ContractRegistry, DAORegistry, ENSContractsRegistry)
    • Analysis:
  • registry-service.ts - Backend API integration
  • Components are UI-only
    • Recommendation: Keep as is - Service and components serve different layers

    Action: Rename for clarity (no consolidation)
